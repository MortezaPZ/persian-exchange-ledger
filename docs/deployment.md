# Deployment, backup, and upgrades

Linux service templates, a TLS proxy, and a private receipt download path are in `deploy/`. This file is not a claim that a public server, a domain, a certificate, a production database, or a restore drill has been run. Access from outside the office needs a machine that stays on, plus network, disk, and certificate renewal.

- The application server is Waitress behind nginx with HTTPS. Do not put `runserver` on the internet.
- Production data is PostgreSQL. SQLite tests do not prove row locks or production concurrency.
- Receipt download requires `VOUCHER_VIEW`. That is the general document-view permission, not a per-customer split. Anyone with it can download every attachment.
- Login throttling, a second factor, security monitoring, and malware scanning of uploads are not in this change. A proxy body limit is not a file-content check. Upload, delete, and every admin path still need a security review.
- The in-app backup is for SQLite only. Do not use it for PostgreSQL. It does not include receipt files.

## Layout

```text
/etc/sarrafi/sarrafi.env           # secrets; root:sarrafi 0640
/srv/sarrafi/releases/<release>/   # immutable source and that release's venv
/srv/sarrafi/current               # symlink to the selected release
/var/lib/sarrafi/                  # writable by the service user, mode 0700
/var/lib/sarrafi/media/            # private receipts, outside the release
/var/lib/sarrafi/staticfiles/      # regenerated by collectstatic
/var/backups/sarrafi/<backup-id>/  # root-only; copy off-site, encrypted
```

Do not put data, media, or backups inside a release. Deleting code must not delete them. PostgreSQL lives in its own data directory. The `sarrafi` system user is not an administrator and has no interactive login. Code is read-only. Data is writable by that user. nginx does not need access to the media directory.

`MEDIA_ROOT` defaults to `SARRAFI_DATA_DIR/media`. Override it with `SARRAFI_MEDIA_ROOT`. On the desktop build, the data folder next to the launcher is the one that counts. Older files may still sit in a previous working directory, including `payment_receipts` beside the source. Find them from the paths stored on `VoucherAttachment`. Copy them into the stable media tree with the same relative path, then check counts and hashes. Changing the setting does not move old files.

Download path:

```text
GET /receipts/<attachment-id>/download/
```

In a template use the named URL for that view. Do not leave `a.file.url`. The response is a forced download, binary, `private, no-store`. An anonymous user is sent to login. A user without permission is forbidden. A missing file is not found. Django does not serve a public media URL, and the nginx sample blocks it. Do not add a public `alias` or `root` for media or for the data directory.

## Server preparation

Templates are in `deploy/`. The commands are for Linux. Review them and run them on a test host. This delivery did not install or reach a server.

1. Install a Python that matches the dependencies, a virtual environment, PostgreSQL, backup tools, nginx, and systemd. Create a dedicated non-superuser database role. Keep the database port on localhost or a private network. Do not publish port 8000.
2. Create the directories and the service user. Place a reviewed source tree in a new release directory. Do not put `.env`, a database, media, a Windows virtual environment, or a real key file in the release archive. The Windows executable is not used on Linux.
3. Copy `deploy/sarrafi.env.example` to the external path with mode `0640` and owner `root:sarrafi`. Fill `SECRET_KEY` and `DB_PASSWORD` privately. The key is at least 50 random characters, unique, and stable across releases. Replace the reserved sample domain in the environment and in the proxy. Do not put the password or the key in shell history, the source archive, or a test report.

The file is plain `KEY=value`, readable by systemd and python-dotenv. No `export`, no `${OTHER_VAR}`. Quote values that contain spaces. `SARRAFI_ENV_FILE` makes management commands load that file. Variables already in the environment win. `DEBUG=false` and `SARRAFI_DESKTOP=false` are required. Production cookies are secure, HTTP redirects to HTTPS, and HSTS is one year including subdomains. Every related subdomain needs a valid certificate. Check the effect of HSTS before turning it on.

4. Create the virtual environment and install dependencies:

```bash
cd /srv/sarrafi/releases/<release>
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Run the checks as the service user. Do not print the real environment. This step does not change the database:

```bash
sudo -u sarrafi env SARRAFI_ENV_FILE=/etc/sarrafi/sarrafi.env \
  .venv/bin/python manage.py check --deploy
sudo -u sarrafi env SARRAFI_ENV_FILE=/etc/sarrafi/sarrafi.env \
  .venv/bin/python manage.py migrate --plan
```

5. Only after the database target, a consistent backup, and the migration plan are accepted, in a maintenance window:

```bash
sudo -u sarrafi env SARRAFI_ENV_FILE=/etc/sarrafi/sarrafi.env \
  .venv/bin/python manage.py migrate --noinput
sudo -u sarrafi env SARRAFI_ENV_FILE=/etc/sarrafi/sarrafi.env \
  .venv/bin/python manage.py collectstatic --noinput
```

Static files are owned by the service user. WhiteNoise reads them. Never copy media into the static directory. Create the first manager through the project's user-admin path, with a private password. Leave no shared password and no sample user enabled.

6. Point `current` at the accepted release. Install the service unit at `/etc/systemd/system/sarrafi.service`. The service listens on `127.0.0.1:8000` and trusts the forwarded scheme only from the local proxy. Install the nginx sample, replace the domain, and have a real certificate and renewal in place before reload. The sample contains no certificate and no private key. The proxy must set `X-Forwarded-Proto` itself. A chain of proxies needs its own trust design.

```bash
sudo systemd-analyze verify /etc/systemd/system/sarrafi.service
sudo nginx -t
sudo systemctl daemon-reload
sudo systemctl enable --now sarrafi
sudo systemctl reload nginx
sudo systemctl status sarrafi --no-pager
```

A local `check --deploy` still warns `security.W021` because `SECURE_HSTS_PRELOAD` is off. Preload is a separate operational decision. It was not enabled to silence the warning. Record that warning in the security review.

These checks have to run on the server. A local reading of the files does not replace them. The sample request-size limit is `10m`. Until login controls and the security review are done, keep the service on a private network or behind network access control.

## PostgreSQL and media backup

A database dump does not keep the files. For a consistent pair, announce the window, point the proxy at a maintenance page, and stop the application and every other writer: bots, scheduled jobs, and management commands. In-flight transactions must finish. Stopping one service is not enough while another writer is still running.

The sample is a local database with peer authentication and a known name. Review it for your host. For a remote database use a service file and a password file mode `0600`, and a connection you have already accepted as encrypted. Do not pass the password as a command argument. The `pg_dump` client must match the server.

```bash
# Run as root during the approved maintenance window.
set -euo pipefail
umask 077
backup_id=$(date -u +%Y%m%dT%H%M%SZ)
backup_dir=/var/backups/sarrafi/$backup_id
mkdir -p "$backup_dir"
systemctl stop sarrafi
# Confirm every other writer has also stopped before continuing.
sudo -u postgres pg_dump --format=custom --no-owner --no-acl \
  --dbname=sarrafi > "$backup_dir/database.dump"
tar -C /var/lib/sarrafi -cpf "$backup_dir/media.tar" media
sha256sum "$backup_dir/database.dump" "$backup_dir/media.tar" > "$backup_dir/SHA256SUMS"
```

If any command fails, do not reopen posting. Record the release name, the time, the database version, the migration state, and the file list beside the backup. Keep configuration and the secret key separately, encrypted, with limited access. Copy the backup off-site encrypted. Define retention and an alert for failure or low disk. A successful `pg_dump` or a matching hash is not a successful restore.

## Restore drill

1. Practice on a new database and an empty media directory. Do not use an automatic wipe against production. Confirm the hash first. The destination owner role must already exist with minimum rights. The names below are the drill only:

```bash
sha256sum -c /var/backups/sarrafi/<backup-id>/SHA256SUMS
sudo -u postgres createdb --owner=sarrafi sarrafi_restore_check
sudo -u postgres pg_restore --exit-on-error --single-transaction \
  --no-owner --no-acl --role=sarrafi --dbname=sarrafi_restore_check \
  < /var/backups/sarrafi/<backup-id>/database.dump
mkdir -p /var/lib/sarrafi-restore-check
tar -tf /var/backups/sarrafi/<backup-id>/media.tar
tar -C /var/lib/sarrafi-restore-check -xpf /var/backups/sarrafi/<backup-id>/media.tar
chown -R sarrafi:sarrafi /var/lib/sarrafi-restore-check
```

2. Point a separate environment at `DB_NAME=sarrafi_restore_check`, a separate data directory, and the restored media. The drill service must not connect to production. Compare row counts, users and roles, document numbers and counters, debit and credit totals per currency, customer balances, trade state, allocations, and deliveries. Check that every named attachment exists, that its hash matches, and that an allowed and a forbidden download behave as expected.

3. A production restore needs the finance owner's approval, every writer stopped, the current state recorded, and a rollback plan. Database and media must come from the same point in time. Prefer a new database and a new path, then switch settings after the check, instead of deleting the current copy first. Rows posted after the backup are lost if you restore an older copy. Preserve them and decide whether to reapply them.

## Moving a test copy from SQLite to PostgreSQL

Copying a SQLite file onto a server is not a PostgreSQL migration. Do not run a command blindly against the live database.

1. Stop every desktop writer and take a consistent copy of the database and the media. If WAL is on, copying the main file alone is not enough. Use SQLite's own backup, or copy only after a clean shutdown and a consistency check. Work on the copy. Leave the original backup untouched.
2. Use the same code and the same migration list. Open the source copy with an explicit temporary environment: `DB_ENGINE=sqlite`, `SQLITE_PATH` pointing at the copy, a temporary `SARRAFI_DATA_DIR`, and a test `SARRAFI_ENV_FILE`. Review the old data before the move. A software fix does not automatically repair earlier wrong allocations.
3. On that isolated source copy you can dump a fixture. The file contains financial data and may contain account data, so keep it encrypted and restricted:

```bash
.venv/bin/python manage.py dumpdata --all --natural-foreign --natural-primary \
  --exclude contenttypes --exclude auth.permission --exclude sessions \
  --output /secure-migration/source.json
```

4. Create an empty PostgreSQL database and a dedicated role. Check `migrate --plan`, then run `migrate` and `loaddata` only on that test destination. If generated rows collide with migrations, or a constraint fails, stop and find the cause. Deleting data or disabling constraints is not the default fix. The fixture stores relative file paths, not file bytes. Copy media separately with the same layout.
5. Match the restore checks. Inspect key sequences and the document-number counter. Post the next document, sign in, check permissions, reports, settlement, and delivery. Sensitive behavior needs a real PostgreSQL concurrency test. After written approval, repeat the same drill on a fresh copy during a posting freeze. Do not experiment on the live copy.

## A new release and a rollback

1. Put the new release in a new directory, install dependencies, and test it. Keep the previous code and both release ids.
2. Open a maintenance window, stop every writer, and take the paired database and media backup. Review the schema plan.
3. With the external environment unchanged, run the accepted migration and `collectstatic` as the service user. Media and backups stay outside the release directory.
4. Move the `current` symlink atomically and restart the service. Before posting resumes, check login, each role, a private receipt, a document, a report, settlement, and delivery.
5. A rollback first confirms that the previous code can run against the new schema. Moving the symlink does not undo a migration. A schema rollback or a data restore follows the tested plan and only while posting is stopped. After new documents exist, restoring an older backup without preserving those documents is not allowed.

Editing the source is not the same as building an executable or deploying. Old executables and archives do not update themselves. A desktop build is a separate delivery.
